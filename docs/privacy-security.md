# Privacy and Security

## Principles

- Data that is never collected is the safest data.
- The SDK does not collect advertising identifiers, email addresses, phone numbers, or precise location by default.
- Do not derive a device fingerprint from IP address, User-Agent, device configuration, network data, or similar signals.
- App operators must be able to explain the purpose, retention period, and destination of every collected field.
- Platform delay, aggregation, noise, and conditional fields are preserved as data-quality metadata.
- SDK input is untrusted even when the SDK is closed or obfuscated.

## Identifiers

### `installation_id`

- Random UUID generated inside the app's local storage
- Scoped to one app
- Resettable through the SDK and removable through a deletion request
- Never joined to a persistent device identifier

### `click_id`

- Random value generated by the redirector
- Links campaign evidence to a click, not a person
- Protected by server-side lookup or an integrity mechanism that detects tampering

### Advertising identifiers

The initial MVP does not collect them. A future adapter may handle one only when its purpose is configured, platform rules permit it, required consent exists, and reset or deletion state is respected. It must not be joined to a persistent identifier.

## Apple

- Tracking across apps or websites requires App Tracking Transparency when Apple's definition applies.
- AdAttributionKit is modeled as privacy-preserving platform attribution, not deterministic user-level attribution.
- Device fingerprinting is prohibited by project policy.
- Verify postback signatures and transaction IDs and reject replayed postbacks.

## Android

- Phase 1 uses Google Play Install Referrer.
- Preserve referrer read time, click time, install-begin time, and validation outcome.
- Never reconnect a deleted advertising ID to an earlier ID or derived profile.
- Add Android Attribution Reporting through an isolated adapter because enrollment, API availability, and report behavior can change.

## Initial retention proposal

- Raw click evidence: 90 days
- Install and attribution records: 25 months, tenant-reducible
- In-app events: 13 months, tenant-reducible
- Audit records: 13 months
- Raw IP at the redirector: not persisted in the application database

Before implementation, legal and operational requirements must validate these defaults. Tenants must be able to choose shorter periods.

## Correction, deletion, and export

- Deletion requests use a control-plane contract, not an analytics event.
- Correction and retraction records identify the affected record, reason, and effective time.
- A valid deletion replaces identifiable raw payloads with redacted tombstones; append-only design is not a reason to retain identifiable deleted data.
- Derived attribution and aggregates are recalculated after deletion.
- Deletion audit records remain separate and irreversibly remove the original subject identifier.
- Request state is `received | processing | completed | failed`.

## Authentication and secrets

- Treat SDK keys as public identifiers with ingestion-only privileges.
- Use separate secrets for management and server-to-server APIs.
- Store secret verifiers, not plaintext secrets, and support rotation.
- Record privileged management operations in an audit log.
- Include the tenant boundary in every query and uniqueness constraint.

## Open-core fraud boundary

Public:

- Fraud-decision schema
- High-level reason taxonomy
- Evidence types and access classifications
- Rule-bundle version and digest fields
- Synthetic fixtures
- Decision and supersession history format

Private and access-controlled:

- Live thresholds and rule combinations
- Model weights
- API and signing keys
- IP, device, and operator watchlists
- Actual evidence values that could identify a user or reveal defenses
- Detection-response timing

Each decision records its reason, evidence references, policy digest, evaluation time, action, and supersession history. Public auditability does not require publishing live attack thresholds.

## Release gates

- Threat model
- Complete SDK field inventory
- Apple Privacy Manifest and App Privacy Details mapping
- Google Play Data safety mapping
- Retention and deletion end-to-end tests
- Dependency and artifact SBOM
- Replay, conflict, tenant-isolation, and redaction fixtures
